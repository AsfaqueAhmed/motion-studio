Phase 6 (`packages/animation`) implemented on branch `phase-6-animation-engine`, built on top of `phase-5-timeline-engine` ([[project_phase5_timeline_engine]]) — branches are linear, none merged to main yet, see [[feedback_phase_branching]].

**Data model** — `IKeyframe`/`IPropertyTrack`/`IAnimationClip` live in `@motion-studio/shared` (`animation.ts`), same convention as `ILayer`/`ITrackItem`. Keyframes have no separate `KeyframeId`: a keyframe's identity within its track is its tick (tick-sorted, tick-unique, enforced by `AnimationEngine`), mirroring how `ITrackItem`s get a per-track invariant rather than needing extra identity machinery.

**`IAnimationClip.layerType` is denormalized from the Layer at creation time** — deliberately, unlike `ITrackItem` avoiding duplicated *mutable* fields (e.g. no `speed`, see [[project_phase5_timeline_engine]]). `layerType` never changes after a Layer is created, so duplicating it is safe, and it lets `AnimatablePropertyRegistry` resolve `(LayerType, propertyKey)` definitions without the Animation Engine importing the Layer Engine's concrete classes (CLAUDE.md "never import each other's concrete classes"). Caller (Editor Service, not built yet) supplies it at Clip-creation time, same as all other caller-supplied IDs.

**Multi-clip blending is explicitly NOT implemented — still open (ADR-005 primitive #3)**. `docs/06-animation-engine/overview.md`'s stub flagged this as needing an evaluation-order/weighting decision before implementation. Rather than half-build it, `AnimationEngine.addClip` throws if the target Layer already has a Clip — today one Layer has at most one AnimationClip. Constraints/Expressions (same open dependency-graph-evaluation problem) are also not implemented, flagged in the same doc section. Do not assume blending or constraint evaluation works before ADR-005 #3 is resolved and a DAG evaluator is built.

**AnimatablePropertyRegistry keyed by `(LayerType, propertyKey)`**, not just `propertyKey` — matches PLAN.md 6.1's literal wording ("per layer type"). Lives in `packages/animation` (not shared) since `interpolate`/`validate` are behavior, not serializable data — `IPropertyDefinition` (`property-definition.ts`) is the Animation-Engine-owned counterpart to shared's data types, same split as `LayerRegistry`/`CompositionGraph` (behavior, in `packages/layer`) vs `ILayer` (data, in shared). `registerBuiltinProperties` seeds every `LayerType` with the `ILayerBase` baseline (`transform.x/y/scaleX/scaleY/rotation`, `opacity`) plus per-type extras (Text: fontSize/color; Shape: fillColor/strokeColor/strokeWidth/cornerRadius; Audio: volume) — matches `IAnimatableLayer` being an `ILayerBase` alias today.

**Easing = named cubic-bezier presets, not a value-space handle model.** Considered modeling `IBezierHandles` as in/out value-space offsets on a keyframe, but simplified to CSS-style `{x1,y1,x2,y2}` control points (`ICubicBezierControlPoints`) solved via Newton-Raphson (`solveCubicBezier`, mirrors the standard `UnitBezier` algorithm) — much simpler, well-understood, and sufficient for PLAN.md's literal ask ("ease-in, ease-out, ease-in-out, custom Bezier"). `bounce`/`elastic`/`back` from the docs stub are explicitly deferred — they oscillate and aren't expressible as a single monotonic cubic-bezier, would need separate Penner-style parametric functions, not in PLAN.md's actual checklist.

**Per-value-type interpolators are separate from per-segment easing.** `InterpolationType` (Linear/Bezier/Step) governs how the raw time fraction becomes eased progress `t`; each `PropertyValueType` has its own `interpolate(a,b,t)` in the registry (`numberLerp`, `vector2Lerp`/`vector3Lerp` unused by any registered property yet, `colorLerp` for `#rrggbb` hex only, `discreteLerp` snap-fallback for Boolean/Text/Gradient/Matrix). Color alpha/named-colors/HSL and true Matrix decomposition are explicitly out of scope, flagged in `docs/06-animation-engine/interpolation.md`. Shape Layer's actual default `strokeColor` is the keyword `"transparent"` (from `@motion-studio/layer` layer-factory) which `colorLerp` can't parse — the registry's own `defaultValue` for that property is `"#000000"` instead, intentionally mismatched (registry default is only the Animation Engine's evaluation fallback, not the Layer's own field default).

**Incremental evaluation via `SegmentLocator`**, one instance per `PropertyTrackId` inside `AnimationEngine`. Caches the last resolved (left, right) keyframe pair; reuses it without a binary search if the next tick still falls in `[left.tick, right.tick)` — the common case during sequential playback. Any keyframe mutation (add/move/delete/modify) invalidates that track's locator. This is scoped as "skip re-search within one track's evaluation," not a whole-Frame-State change-tracking cache across Layers — that's left to whatever builds Frame State later (Rendering Engine, Phase 7), see `docs/06-animation-engine/timeline-binding.md`.

**`evaluateAt(layerId, propertyKey, tick)` returns `undefined`** (not a thrown error) when the Layer has no Clip or the property has no track — callers are expected to fall back to the Layer's own static field value. No Editor Service/Frame State builder exists yet to actually do that fallback or to drive Timeline-tick → Animation-evaluation binding — flagged as an open wiring gap in `docs/06-animation-engine/timeline-binding.md`, same shape as [[project_phase5_timeline_engine]]'s Playhead/Scheduler wiring gap.

Full monorepo `pnpm build`/`pnpm lint`/`pnpm test` all pass after this phase (16 packages incl. `apps/studio`, no regressions; 56 new tests in `@motion-studio/animation`). Hit real TypeScript strictness issues from this repo's `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` (both on in `tsconfig.base.json`) while implementing `SegmentLocator` (array indexing) and `ModifyKeyframeCommand`'s undo-snapshot (had to build the "before" snapshot via object-destructuring rest rather than explicit property assignment, so an absent `bezierControlPoints` doesn't become an explicit `undefined`) — worth remembering these two flags are strict in this repo when writing array-heavy or optional-field code in any future phase.
